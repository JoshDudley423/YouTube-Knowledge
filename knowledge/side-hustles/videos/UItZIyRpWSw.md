# Watch Me Build an App With AI and Make a Sale in 85 Minutes
Channel: The Koerner Office | https://www.youtube.com/watch?v=UItZIyRpWSw | Published: 2026-09-02

Live build-in-public episode: host (no coding background) builds and launches a real SaaS product end-to-end using AI "vibe coding" tools, then markets it without leveraging his existing audience, and lands a real paying customer. This is a tactical/tooling case study more than an "idea" episode — dense in specific tools, prompts, and workflow steps.

## The product idea: "OnlyWaivers" — niche digital liability-waiver SaaS
- Problem (host's own, real pain point): as a leader in his church (LDS/Mormon), he regularly needs 60-70 youth to sign paper liability waivers for activities — PDFs get printed, lost, forgotten; existing e-signature tools (DocuSign, etc.) are too generic/cumbersome for this specific narrow use case.
- Product: create an event, optionally upload your organization's own waiver PDF (or use a generic provided one) with required custom fields, generate a shareable link, recipients just add a name and tap-to-sign (no login needed for signers, only for the event organizer/admin), organizer gets all signed copies in an admin dashboard.
- **Pricing**: $13/year subscription or $17 lifetime (deliberately made the lifetime option attractive because of subscription fatigue — thesis: better to capture $17 once than risk $0 from someone unwilling to subscribe; early lifetime buyers get grandfathered in even if the tier is later removed, as a reward for "trusting early"). No free tier — but the funnel lets users get all the way to generating the shareable link before requiring payment (an explicit "sunk cost" tactic: once someone has invested ~2 minutes building their waiver/link, they're more likely to pay rather than abandon).
- Initial wedge/niche: marketed first specifically to LDS ward/stake activity leaders (a narrow, well-defined, values-aligned audience the host understands deeply) rather than the broader addressable market (gyms, tour operators, camps, sports leagues) — explicit strategy: start with the audience closest to the exact problem you personally have, even though other verticals might convert cheaper/easier, because you already have the domain knowledge and messaging.
- Note: Meta/Facebook disallows religion-based ad targeting, so LDS-specific messaging had to be done through ad copy/language (using insider terms like "ward," "stake," "youth conference") rather than targeting parameters.

## Toolchain used (concrete, named)
- **Namecheap** — bought the domain (onlywaivers.com, $12).
- **Replit (Agent 4, using Claude "Opus"-class model referred to as "Fable 5")** — the vibe-coding platform actually building the app from natural-language prompts; iteratively builds, publishes, and self-fixes bugs. Host explicitly does NOT use Claude Code because a terminal interface is "too technical" for his comfort level, despite being non-technical overall.
- **Claude (chat)** — used as a prompt-engineering layer: host describes the idea informally to Claude first, and Claude writes a more complete, structured spec/prompt (covering legal audit-trail requirements, IP-address logging for signature validity, PDF-emulation as the hardest technical piece, link-expiration handling, using Stripe test mode until the flow is bulletproof) which is then pasted into Replit. Also used as an orchestration layer via MCP connections into other tools (see below).
- **MCP (Model Context Protocol)** connections used live: Facebook Ads (official Meta MCP), Stripe, Google Drive, Beehiiv (email), Gmail, Google Calendar, Google Analytics, Resend/SendGrid (transactional email), Twilio (SMS, mentioned but not used to reduce friction). Host also lists other MCPs he has connected in daily life (Whoop, Fathom notetaker, Function Health, Gusto payroll, Robinhood, Plaud pendant recorder, Kubera net-worth tracker, GoHighLevel, Higsfield, Zapier, TypeForm) as an aside on how broadly MCPs can integrate AI into existing tools.
- **Stripe** — payment processing; two products created programmatically ($13/yr, $17 lifetime). Required both a "secret" and a "publishable" API key; live-mode connection required going through Replit's Stripe integration/app-install flow specifically (not just pasting API keys), which was the single biggest technical snag of the whole build (see caveats).
- **SendGrid / Resend** — transactional email (organizer alerts, waiver copies); host treats these as an interchangeable commodity layer.
- **Google Analytics** (GA4) — added via one prompt/tag for real-time traffic and funnel visibility (pricing page, "create a waiver" step, form start, etc.).
- **Meta Pixel** — added for ad conversion tracking (view content, initiate checkout, purchase events); host also had Claude generate a prompt for **server-side purchase-event reporting** so tracking survives ad blockers.
- **Meta Ads Manager** (Facebook/Instagram ads) — campaign, ad set, and ad created almost entirely by prompting Claude via its Facebook Ads MCP (host never touched the ads UI directly for creation) — includes campaign budget optimization (CBO), traffic objective, "Advantage+ audience expansion" deliberately turned OFF to keep a narrow, specific targeting match rather than let Meta's automatic broad-targeting AI take over, age range 20-60, US-based.
- **DJI Mic 3** wireless lav mic + iPhone front camera — used to record a single-take, unedited ~30-second vertical ad video (no captions, no thumbnail edits) speaking directly to the niche audience using insider language.
- **Meta Ad Library** (public tool) — used to verify whether/how an ad is publicly visible once live.
- **Teleprompter app** (~$20/year) — mentioned as an option for scripted takes, not used for this ad.

## Numbers from this specific build
- App had a basically complete, live, and monetizable MVP within roughly **20-30 minutes** of initial Replit prompting (per host's own real-time commentary), full session (including debugging, marketing setup, ad iteration) spanned the video's ~85-minute framing, with additional follow-up work over subsequent days (host also references "last week I spent 3 hours building this" and later touch-ups).
- Ad spend: initial daily budget started at $20/day, later increased to **$200/day** "to get results as soon as possible" while payments were still broken.
- Cost metrics observed and discussed live: cost per landing page view started around **$1.49-$1.50**, dropped to **$0.65** within ~10 minutes as Meta's algorithm optimized; cost per click ~$0.47-$0.96; click-through rate started around **1%**, later ticked up to ~1.3-1.5% on larger ad variants and briefly spiked to 7.3% (small sample) on Utah-specific impressions, and one particular ad variant reportedly showed a 20% CTR (very small sample, called out as unreliable).
- Total ad spend before securing the first real paying customer: **~$100** (explicitly acknowledged as a net loss against a single $13 sale, on top of ~6 hours of build time) — host frames this positively as "sell it before you have it" and treats it as a worthwhile, asymmetric bet rather than a failure.
- First real paying customer: $13/year subscription, from a stranger in Idaho (not from the host's own test purchase, and not from his own audience) found via the Facebook ad, confirmed live in Stripe during the recording — this is the concrete proof point the video's title refers to.
- Break-even math cited: at $200/day ad spend generating ~100-200 landing page views/day, the host estimated needing roughly "15 sales a day" to break even on ad spend alone in the short term — explicitly accepted as unprofitable on day one/week one, betting instead on word-of-mouth/referral virality (waiver-recipient emails include a referral link back to the product) and multi-year lifetime value rather than short-term ROAS.

## Process / step-by-step approach demonstrated
1. Identify a real, personally-experienced problem as the idea source (not a manufactured one) — "be your own first customer."
2. Buy a simple, memorable .com domain immediately, before building anything.
3. Use a general-purpose AI chat (Claude) to turn a rough idea description into a structured build prompt for the vibe-coding tool (Replit), explicitly naming the target platform so the AI tailors its guidance ("tell your prompt the name of the app you're using to vibe code").
4. Don't overthink the first prompt — "any prompt is better than no prompt"; perfectionism is the friction that stops people from starting.
5. Build and market in parallel, not sequentially — start setting up ad campaigns and creative while the app is still being built ("sell it before you have it").
6. Reduce every point of friction to conversion (no login required to generate a waiver link, defer payment until after value is partially delivered) while adding just enough friction to cancellation/refund-abuse (not covered in depth here, more referenced conceptually).
7. Treat AI agent refusals skeptically — "if Claude says it can't do something, it doesn't mean it can't; it just doesn't want to spend compute/credits — push back."
8. Add trust signals for a brand-new, unproven product: embed the same ad video on the landing page (proves it's not bait-and-switch), pull founder bio/credibility content from an existing personal site, offer a "100% lifetime money-back guarantee, no questions asked."
9. Multi-channel organic launch alongside paid ads: post in relevant niche Facebook groups (posts with an image/screenshot perform better) and targeted subreddits. Reddit-specific tactic described: **write a true, honest personal story without linking or naming the product initially**; only add the link/name later once the post has organically proven engagement (upvote ratio, comment sentiment) — moderators are far less likely to remove a link added after a post already has traction, since removing it at that point looks like it would do more harm than good to community goodwill. Also: identifying and prioritizing larger AND more actively-engaged subreddits (compared subscriber count and weekly-contributor ratio between two candidate subreddits to pick the better one).
10. Use Meta Ads Manager's custom "columns" view to build a saved reporting preset showing only the specific metrics that matter (cost per landing page view, 3-second/15-second video plays, cost per unique click) instead of the cluttered default view.
11. When ad performance data revealed delivery skewing to non-target states (Meta's algorithm chasing cheap clicks broadly rather than respecting the LDS niche intent), the host caught it via the geographic breakdown report and had Claude/Replit-adjacent tooling narrow targeting to Utah specifically — illustrating that "let the algorithm decide" isn't always correct and manual oversight/course-correction is still necessary.
12. Iteratively duplicate/A-B test ad variants (5 headline/text/description variations) via a single Claude prompt to the Facebook Ads MCP, rather than manually creating each variant — with the caveat that any copy change technically counts as new creative and can trigger platform re-review.

## Caveats and things that went wrong (realistic friction, not just highlight reel)
- The single biggest recurring blocker was the **Stripe live-mode connection**: simply pasting API keys into Replit was not sufficient — required going through Replit's dedicated Stripe app-install/OAuth flow ("claim sandbox," install the Replit app on the live Stripe account) multiple times before payments actually worked in production; multiple false "it's fixed now" assurances from the AI agent that turned out not to be true.
- Confusion between Stripe's "secret key" vs. "publishable key" cost real time — the agent (Claude) had to explicitly clarify only the secret key was required for this server-side use case.
- A media/upload glitch caused the ad video to initially get associated with the wrong ad account, requiring re-upload.
- The Meta ad had to go through platform review before going live/serving; editing a live ad (even minor copy) can trigger re-review taking minutes to hours — a reason to batch/avoid unnecessary edits once an ad is approved and running.
- Contact-us form broke at one point due to switching email providers (SendGrid to Resend) mid-build; fixed with a single follow-up prompt.
- Host is explicit that the underlying core product (the actual waiver-signing/data-collection form) was still fairly rough at time of first sale — v1 only collected a name and signature; a more complete version (address, emergency contact, medical/allergy info with a "none of these apply" default to reduce friction) was added afterward via a single detailed Claude-drafted prompt. Frames this as acceptable: **getting paid is more urgent/important than the product being fully polished**, since payment infrastructure issues are harder to "fix later" than product gaps.
- General honesty/ethics note: host explicitly told the AI not to fabricate a founding story or fake credibility claims (e.g., rejected an AI-drafted Reddit post because it contained an untrue narrative) — advises always double-checking AI-generated marketing copy for factual accuracy.
- The video is explicit that this was a real, ongoing business the host intends to keep running/expanding beyond just the LDS niche (repositioning to other waiver-needing markets like gyms/camps/tours is described as trivial — "one or two prompts" — once initial traction with the wedge audience is proven).
